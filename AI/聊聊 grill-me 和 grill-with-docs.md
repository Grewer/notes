# 聊聊 grill-me 和 grill-with-docs

前几天改本地 skill 的时候, 又碰到一个老生常谈的问题: 很多 AI agent 会卡在需求还没问清楚的时候, 太早开始写代码

这点在复杂需求里会很明显。人说一句"帮我设计一下这个方案", agent 很快给出一版看起来挺完整的方案, 但里面可能混着几个没确认过的前提: 业务词是不是这么叫, 边界是不是这样切, 数据归属在哪, 失败场景要不要 cover。等写到一半再发现前提错了, 返工成本就上来了。

所以本期就来聊聊两个我最近在本地用的 skill:

- `grill-me`: 用来追问一个方案, 把决策树问清楚
- `grill-with-docs`: 在追问方案的同时, 顺手检查项目里的领域文档和决策记录

总的来说, 这两个 skill 的目标很朴素: 让 AI 别把不该默认的东西默认掉。

## grill-me: 先把决策树压出来

`grill-me` 的核心动作很直接: 围绕一个计划或设计连续追问, 直到人和 agent 对方案有同一套理解。

这里的重点不在"苏格拉底式提问"这种听起来很玄的东西, 重点在一个更工程化的流程:

1. 先看这个方案里有哪些分叉
2. 判断哪些分叉之间有依赖
3. 先问会影响后续路径的问题
4. 对每个问题给一个推荐答案
5. 对明显能从代码、约定、用户原话里推出来的答案, 直接采用, 但最后列出来

举个很常见的例子。我们要做一个上传能力, 用户只说了"支持大文件上传", 这句话里其实藏着很多分叉:

- 大文件是 100MB, 1GB, 还是 10GB?
- 是前端直传对象存储, 还是业务服务中转?
- 失败后要不要断点续传?
- 同一个文件重复上传怎么处理?
- 权限校验发生在拿 token 前, 还是上传完成后?
- 进度条要准确到 chunk 级别, 还是整体进度即可?

普通 agent 很容易直接写一个"分片上传 + 进度条 + 重试"的方案, 看起来没问题, 但其实已经替人做了几个决定。`grill-me` 要做的就是把这些隐含决定摊开, 然后按依赖顺序处理。

比如"前端直传还是服务端中转"会影响接口设计和鉴权, 这个要早问。"进度条是不是 chunk 级别"通常只是体验细节, 如果项目里已有上传组件, 也许直接沿用现有模式就行, 没必要一上来打断用户。

这种追问方式适合几类场景:

- 新功能方案还没定, 但已经要开始拆实现
- 技术方案里有几个不可逆或返工大的选择
- 用户的描述里有业务词, 但词的边界不清晰
- 需求看起来简单, 但实际会影响多个模块

不适合的情况也很明确。如果只是修一个报错, 或者改一个确定的 UI 文案, 直接做就行, 没必要为了"流程感"硬 grill 一遍。

## 它和普通澄清问题的区别

普通澄清问题经常是这样的:

```text
你希望怎么处理失败场景?
你希望怎么做权限控制?
你希望怎么展示进度?
```

这些问题没错, 但对用户来说压力很大。因为 agent 把判断都扔回去了, 用户还得自己想选项。

`grill-me` 会要求每个问题都带推荐答案。比如:

```text
问题: 上传失败后是否需要断点续传?
推荐: 如果文件上限在 200MB 以内, 先做整体重试即可, 不做 chunk 级断点续传。原因是当前复杂度主要在 token 和权限校验, 断点续传会引入额外状态。
```

这个差别比较关键。提问只是一层外壳, 真正有用的是让人更快做判断。推荐答案不一定最后被采纳, 但它能把讨论从"你想要什么"推进到"这个默认值合不合理"。

我现在更喜欢这种格式, 因为它更接近实际 code review 或方案评审。一个工程师不会只抛问题, 他会说"我建议这么做, 但这个地方有个 tradeoff"。agent 也应该这样。

## grill-with-docs: 把领域语言一起拉进来

`grill-with-docs` 比 `grill-me` 多一层约束: 它不只问方案, 还会检查项目里已有的领域语言和决策记录。

它默认会看几类文件:

- 根目录的 `CONTEXT.md`
- 多上下文项目里的 `CONTEXT-MAP.md`
- `docs/adr/` 里的 ADR
- 必要时再结合代码里真实存在的概念

这里的 `CONTEXT.md` 不是需求文档, 也不是技术方案, 它更像一个项目内的 glossary。比如一个项目里决定把"下单的人"叫 `Customer`, 而不是 `Client` 或 `Buyer`, 那这个约定应该在 `CONTEXT.md` 里。后面讨论需求时, 如果用户突然说"account", skill 就要追问: 这里说的是 `Customer`, 还是登录系统里的 `User`?

这类问题很容易被忽略, 但长期看很值。很多项目的复杂度不是来自代码行数, 而是来自词被用乱了。同一个词在产品、前端、后端、数据侧各有一套含义, agent 如果不先把词拉齐, 后面写出来的方案就会越跑越偏。

`grill-with-docs` 会做几件事:

1. 如果用户用了一个和 `CONTEXT.md` 冲突的词, 直接指出冲突
2. 如果用户用了模糊词, 给一个更准确的 canonical term
3. 用具体场景压测边界, 比如取消订单时是否允许部分取消
4. 用户说某个行为存在时, 去代码和文档里确认是否真是这样
5. 一个术语确定后, 立刻更新 `CONTEXT.md`
6. 一个决策值得记录时, 才创建 ADR

这里有两个边界比较重要。

第一, `CONTEXT.md` 只写领域语言, 不写实现细节。不要把它写成"系统如何处理订单取消", 只写"Cancellation 在这个上下文里是什么意思, 避免叫成什么"。

第二, ADR 不要滥用。只有同时满足三点才写:

- 以后反悔成本高
- 没上下文的人会觉得这个选择奇怪
- 当时确实有几个可选方案, 最后做了取舍

如果只是一个显而易见的小决定, 就不需要 ADR。文档一旦变成垃圾桶, 后面没人会读。

## 一个更具体的场景

假设我们在做工单系统里的"撤回"能力。用户说:

```text
帮我设计一下撤回逻辑, 已经流转到下一节点的工单也要支持
```

`grill-me` 可能会先问:

- 已经被下一节点处理过的工单还能撤回吗? 推荐默认不允许, 因为会破坏处理人的操作记录
- 撤回后回到哪个节点? 推荐回到发起人草稿态, 避免出现"悬空节点"
- 撤回需要通知谁? 推荐通知当前处理人和发起人, 不扩散给历史处理人

`grill-with-docs` 会继续看项目语言:

- 文档里已有 `Reopen`, `Cancel`, `Rollback`, 当前的"撤回"到底对应哪个?
- `CONTEXT.md` 里是否已经定义了 `Ticket` 和 `Task` 的区别?
- 代码里如果只有"整单取消", 用户说的"撤回某个节点"是不是一个新概念?
- 这个决策会不会影响后续审计, 如果会, 是否需要 ADR?

这就是两个 skill 的差别。`grill-me` 主要压方案分支, `grill-with-docs` 还会把项目自己的语言和历史决策拉进来, 防止我们在错误的词上继续讨论。

## 什么时候用哪个

简单来说:

| 场景 | 更适合 |
|------|--------|
| 只是想把方案问清楚 | `grill-me` |
| 项目里有明确领域模型, 术语容易混 | `grill-with-docs` |
| 需要边聊边补 `CONTEXT.md` | `grill-with-docs` |
| 只是一次轻量脑暴 | `grill-me` |
| 会产生难以反悔的架构选择 | `grill-with-docs`, 并考虑 ADR |

如果不确定, 我会先用 `grill-me`。一旦发现讨论里开始出现领域词, 或者方案取决于历史决策, 再切到 `grill-with-docs`。

## 我的优化版本

原始的 grill 类 skill 很容易走向另一个极端: 每次只问一个问题, 等用户回答后再问下一个。这个流程严谨是严谨, 但实际用起来有点慢, 尤其是很多问题彼此独立时, 一问一答会把节奏切得很碎。

我现在本地版主要做了几处调整。

### 1. 独立问题批量问

如果几个问题互不影响, 或者都属于同一个决策区, 就一次性问出来。默认控制在 3-7 个问题一批, 不把用户淹没, 也不让对话变成挤牙膏。

只有几类情况保留单问:

- 当前答案会决定下一个问题怎么问
- 这个决定高风险或者难反悔
- 批量问会让用户回答不清楚
- 问题本身有强依赖, 先后顺序不能乱

这样改完之后, 交互更接近日常评审。一个 topic 下的问题放在一起看, 用户也更容易发现"这几个其实是一类"。

### 2. 每个问题都给推荐答案

现在不会只问:

```text
要不要支持断点续传?
```

会直接给判断:

```text
要不要支持断点续传?
推荐: 先不支持。当前文件大小上限不高, 整体重试能 cover 大部分失败场景, 断点续传会引入 chunk 状态和清理任务。
```

这个推荐答案很重要。它逼着 agent 自己先做一次判断, 而不是把所有不确定性都甩给人。人类要做的是 review 这个判断, 而不是从零开始补方案。

### 3. 能从上下文推出来的答案不再问

如果用户原话、代码库、项目约定或低风险默认值已经能回答, 就直接采用推荐答案。比如项目里已有上传组件, 并且所有入口都走同一套 token 逻辑, 那就不需要再问"上传 token 怎么拿"。

但是这些自动采用的答案不能悄悄吞掉, 最后要列出来:

```text
自动采用:
- 上传鉴权沿用现有 getUploadToken 流程, 因为当前仓库已有统一封装
- 失败重试沿用现有组件默认策略, 不新增断点续传
```

这样用户还有机会纠正, 同时不会被低价值问题打断。

### 4. grill-with-docs 保留自己的文档边界

`grill-with-docs` 也同步了上面的批量提问和自动消解逻辑, 但没有动它自己的领域文档规则。

也就是说, 它仍然坚持:

- `CONTEXT.md` 只记录领域词, 不写实现方案
- 术语确定后可以 inline 更新, 不攒到最后
- ADR 只在真正值得记录时创建
- 代码和文档冲突时要指出来, 不能假装一致

这个保留很关键。否则它就会退化成一个"会顺手写文档的 grill-me", 但真正有价值的是它能把方案讨论和领域模型放到一起校验。

## 总结

本文主要介绍了 `grill-me` 和 `grill-with-docs` 两个 skill 的区别, 以及我现在本地版做的一些改动。

总的来说, `grill-me` 适合把方案里的隐含决策问出来, `grill-with-docs` 适合在有领域语言和历史决策的项目里使用。在我的优化版本里, 我更倾向于让 agent 批量问独立问题、给推荐答案、自动消解明显问题, 最后再把采用的默认值列出来。

这套东西不一定适合所有任务。小修小补直接做就行。但一旦需求里开始出现多个分叉、多个业务词、多个模块边界, 先 grill 一轮, 基本能省掉后面不少返工。
